## 4. 技术栈【已确认】

**Python 官方 SDK（`mcp` 包）**，不再用 TypeScript。

已核实的能力边界：

| 能力 | Python 官方 SDK | 课程可用性 |
|---|---|---|
| 工具定义 | `@mcp.tool()` 装饰器 + 类型注解 → Pydantic 自动生成 JSON Schema | ✅ 比 TS 简洁，适合零基础 |
| 传输 | stdio（默认）/ SSE / Streamable HTTP（`run(transport=...)`） | ✅ 与 TS 版一致，已实测 |
| **MRTR 人类确认** | 新协议 `InputRequiredResult`；老协议 `ctx.elicit()`；同一个 handler 自动适配 | ✅ **完全支持**，可做进阶任务 |
| Tier 地位 | TypeScript / Python / Go / C# 均为 Tier-1，规范落地当天同步 | ✅ 长期稳定 |

三个必须写进课程提示的坑（前两条**已实测验证**）：
1. **官方包 `mcp` 与第三方的 `fastmcp`（gofastmcp.com）是两个不同的东西**，装错就一路报怪错。
2. **`mcp` 2.x 把 v1 的 `FastMCP` 改名成 `MCPServer`**，导入路径从 `mcp.server.fastmcp` 变成 `mcp.server.mcpserver`。
   照 v1 老教程写会直接报错（SDK 会给出明确的迁移提示；也可 `pip install "mcp<2"` 回退）。
   **课程骨架已按 2.x 写，并用真实 stdio 握手验证通过**（`list_tools` → `['hello']`；`call_tool` → 「你好，同学！MCP 服务器已就绪。」）。
3. Python 的 MRTR 写法（`Resolve`/`Elicit` 标记或 `ctx.elicit`）与 TS 完全不同，**不能照抄 TS 代码**。

> 实测环境：`mcp 2.2.0` + Python 3.13（隔离 venv），验证方式为官方 client 的 stdio 握手 + 工具调用。

存储层：**SQLite**（Python 标准库 `sqlite3`，零额外依赖、零原生编译），不引入 Postgres。

## 6. 验收证据设计：全部走 GitHub

这是本次需求的核心变化——**平台不做表单，学生的所有产出都落在自己的 GitHub 仓库里**。

### 6.1 证据清单

| 证据 | GitHub 上的位置 | 能证明什么 | 客观性 |
|---|---|---|---|
| 代码 | 仓库源文件 | 功能是否实现 | 高 |
| 单测/测试脚本 | `test/` 目录 | 是否写了测试 | 高 |
| **测试报告** | 仓库根目录 `TEST_REPORT.md` | 测试覆盖、Expected vs Actual | 中（学生自述，靠细节具体性判） |
| **Issue 记录** | GitHub Issues | 是否真的发现并描述了问题 | 中高（自带时间戳） |
| 修复 | `git log` / commit | 是否真的改了 | 高 |
| 回归结果 | GitHub Actions 运行结论 | Fix 后是否不回归 | **最高**（system 判定，CI 直判） |
| 使用痕迹 | **sqlite 库导出文本**（贴在报告里） | 是否真的用了、用了几天 | 高（数据库是程序自己写的，时间戳与记录数难伪造） |
| 可选辅助 | 客户端截图 | AI 确实调用了工具 | 低（仅辅助） |

### 6.2 关键设计：不做表单，怎么收报告？

**报告就是仓库里的一个 Markdown 文件**（`TEST_REPORT.md`），学生用 PR 或直接 commit 提交。平台在评审时通过现有的 GitHub 证据链自动拉取它——**零表单、零存储、零数据库**。

测试报告模板（学生直接照抄进 md，5–8 条案例）：

```markdown
| # | 测试场景 | 输入 | 预期结果 | 实际结果 | 是否通过 | 问题描述 |
|---|---|---|---|---|---|---|
| 1 | 保存明确决定 | "我们决定采用 RAG 架构" | 落库为 decision，置信度 ≥0.7 | ✓ 决定(置信 90%) | PASS | |
| 2 | 模糊想法识别 | "可以考虑加缓存" | 标记为需人工确认 | 误判为 commitment | FAIL | #7 |
```

**其中「实际结果」是最有价值的一栏**——它反映真实用户到底怎么用这个工具。

### 6.3 客观性补强（防"自说自话"）【建议】

单靠自述无法证明"学生真的用了"。用三个客观锚点补强：

1. **sqlite 导出**：`sqlite3 work-continuity.db "SELECT status, kind, created_at FROM commitments"` 的输出贴进报告 → 记录数、状态分布、**时间跨度**（跨 ≥2 天）一次性证明。
2. **commit / Issue 时间戳**：跨 ≥2 个工作日必须是**真实的日历跨度**（git 记录可查）。
3. **报告细节的具体性**：必须给出报错原文、工具返回原文、Issue 编号。Rubric 明确评价"证据是否具体可核对"，而不是"结论是否正确"。

> 接受一个现实：**无法 100% 防伪造**。所以 Rubric 评的是"测试是否充分、描述是否准确"，不是"是否发现了第 17 号 Bug"（沿用方案 §17 的原则）。

## 7. 平台引擎需要的新增能力

| # | 改动 | 必要性 | 说明 |
|---|---|---|---|
| 1 | **扩展关键文件拉取规则**：新增"报告类"（`TEST_REPORT.md`、`BUGS.md`、`REPORT.md`…）与"测试类"（`test_*.py`、`tests/`）文件组，并把报告类优先级排在 README 之前 | **必须** | 实测现状：`_pick_key_files` 只从根目录按 README/依赖/主入口/配置 四组选最多 8 个文件，**拉不到测试报告** |
| 2 | 报告类文件放宽行数上限（120 → 约 250 行） | **必须** | 报告是表格，120 行不够 |
| 3 | **新增 `report` 证据类型**：评审 Prompt 里按表逐条核对"学生声称 PASS 的项，实际结果是否支持" | 建议 | 否则报告只会被当普通自述读一遍，兑现不了方案价值 |
| 4 | GitHub Issues 拉取（可选） | 建议 | 拉 Issue 标题 + 正文 + 时间戳，作为 Stage 4 证据；不做也可用报告里的 Issue 编号替代 |
| 5 | 课程 Rubric 素材（题库/大纲） | 必须 | 走正常课程开发流程 |

**明确不做**：不建表单、不建仓库、不建数据库、不做文件上传、不做过程录屏。
