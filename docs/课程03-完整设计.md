### 项目一简历素材
- **resume_intro**：用 Python 与官方 MCP SDK 实现一个跨会话项目记忆服务：把对话中的决定、承诺、问题结构化为可检索记录，通过 SQLite 持久化并暴露为一组 MCP 工具供 AI 客户端调用。
- **resume_tech**（纯技术名词）：`Python`、`MCP（Model Context Protocol）`、`官方 mcp SDK`、`SQLite`、`JSON-RPC`、`stdio`、`pytest`、`GitHub Actions`
- **resume_points**（难点 + 目的 + 结果）
  - 定义 6 类记忆与状态机并对非法迁移做校验｜避免状态乱跳导致数据不可信｜保障了记忆库的一致性 → `architecture`
  - 用规则 + 置信度阈值分类自然语言，低置信交人工确认｜避免把随口一说当成正式承诺｜减少了误记 → `architecture`
  - 建表与迁移写成幂等脚本｜让老库能平滑升级、重复执行不炸｜保障了可重复部署 → `stability`
  - 暴露为 MCP 工具并写清用途说明｜让 AI 能自主判断何时调用｜工具被选中的准确率提升 → `delivery`

### 项目一面试自检题
1. **explain**：MCP 的 tools / resources / prompts 三者区别？你的项目为什么用 tools？
   - 锚点：tools 是模型主动调用并可能有副作用；resources 是客户端拉取的只读数据；prompts 是用户主动触发的模板。
2. **debug**：客户端里看不到你的工具，你会按什么顺序排查？
   - 锚点：先看客户端配置的 command/args 是否能手动跑通 → 再看启动日志有没有报错 → 再看协议版本/transport 是否匹配。
3. **transfer**：如果要让"记忆"支持多台机器共享，你会怎么改？
   - 锚点：换掉存储后端（如网络数据库）或把服务改成 HTTP 传输，注意并发与鉴权。

## 5. 验收证据规范（全部走 GitHub）

| 证据 | 位置 | 证明什么 | 客观性 |
|---|---|---|---|
| 代码 / 测试 | 仓库源文件、`tests/` | 功能是否实现、是否写了测试 | 高 |
| **测试报告** | 根目录 `TEST_REPORT.md` | 测试覆盖度、Expected vs Actual | 中（靠细节具体性判） |
| **Issue** | 仓库 Issues | 是否真的发现并描述问题 | 中高（自带时间戳） |
| 修复 | `git log` | 是否真的改了 | 高 |
| 回归 | **GitHub Actions 结论** | 修复后是否不回归 | **最高（system 判定）** |
| 使用痕迹 | 贴进报告的 sqlite 导出 | 是否真的用了、用了几天 | 高 |
| 截图（可选） | 客户端界面 | AI 确实调用了工具 | 低，仅辅助 |

**客观性补强**（防"自说自话"）：数据库导出（记录数 + 时间跨度）、commit/Issue 的真实日历跨度、报告里必须出现报错与返回原文。
**接受现实**：无法 100% 防伪造 → Rubric 一律评「测试是否充分、描述是否准确」，**不评"是否找到了指定 Bug"**。
