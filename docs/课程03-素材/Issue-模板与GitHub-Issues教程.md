# 怎么用 GitHub Issues（+ 提交模板）

课程 03 要求你把测试中发现的问题**真的提成 Issue**（不是只写在报告里）。别慌，一个 Issue 就 30 秒。

---

## 一、Issue 是什么

GitHub 仓库上方的 **Issues** 标签，就是一个「问题与讨论区」。每个 Issue 有：

- 一个**编号**（如 `#7`）—— 这就是你要提交的证据
- 一个**创建时间** —— 客观记录，改不了
- 标题 + 正文 + 可选的标签（`bug` / `enhancement` / `question`）
- 状态（open 开启 / closed 关闭）

---

## 二、怎么创建（网页版，30 秒）

1. 打开你的仓库页面
2. 点上方 **Issues** 标签 → 绿色 **New issue** 按钮
3. **标题**写清「什么东西坏了」或「哪里不合理」
4. **正文**按下面模板填
5. 右侧可加标签（不是必须）
6. 点 **Submit new issue** → 拿到编号，例如 `#7`

> 记下这个编号：测试报告的「关联 Issue」栏要填它，修复时的 commit 信息里也要引用它。

---

## 三、两种 Issue 都算数（重要）

| 类型 | 例子 | 算不算数 |
|---|---|---|
| **Bug** | 「保存决定时偶尔丢记录」 | ✅ 算 |
| **产品反馈** | 「idea 和 plan 的区别不明显，我不知道该用哪个」 | ✅ **同样算** |

> 别觉得「这不是 bug 就不算」。真实工程里，**设计不合理的反馈和 Bug 一样重要**——
> 很多问题不是代码写错了，而是设计让人用不明白。

---

## 四、模板 A：Bug 报告

```text
### 环境
- 操作系统 / Python 版本 / mcp 包版本：
- 使用的客户端与版本：
- 数据库文件：

### 复现步骤
1.
2.
3.

### 预期结果
（你以为会发生什么）

### 实际结果
（实际发生了什么 —— 把报错原文**整段贴上来**，不要只写「报错了」）

### 补充
（截图 / 日志 / 已尝试过的排查，可选）
```

---

## 五、模板 B：产品反馈

```text
### 我在做什么
（当时的真实场景，例如「我在对话里说‘以后再加用户反馈模块’」）

### 哪里不顺手
（具体到操作，例如「连续两次都被归成了 commitment，但我其实只是想记个 idea」）

### 我期望的方式
（如果让你改，你会怎么改）

### 影响
（这个不顺手会导致什么后果，例如「记忆库里堆了一堆不该被当成承诺的东西」）
```

---

## 六、提交之后

1. **修复时引用编号**：commit 信息写成 `fix: 修正模糊语言的分类阈值 (#7)`，GitHub 会自动把提交和 Issue 关联起来
2. **修复验证后关闭 Issue**：在 Issue 里写一句你是怎么修的、怎么验证的，然后 Close
3. 如果修不完，也**如实保留在 open 状态**并在报告里说明 —— 这比假装没问题更专业

---

## 七、常见疑问

**Q：仓库里没有 Issues 标签？**
A：说明 Issues 被关闭了。到仓库 **Settings → General → Features** 里勾上 Issues。

**Q：可以提几个？**
A：至少 1 个。多提不扣分，但**每个都要写清楚**，凑数量没意义。

**Q：提了 Issue 但后来发现是我自己理解错了？**
A：正好——在 Issue 里说明你的排查结论，然后关闭它。**这也是一次合格的工程过程记录。**
