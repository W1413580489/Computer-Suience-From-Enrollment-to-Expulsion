## 1. 项目一句话定义

**当前状态的一句话定义**：

> 一个面向暨南大学信科院学生的校园 Web 站点：学生用"假登录"建立本地身份 → 看到按年级个性化的校园指南页面 → 可以用自带 API Key 的 AI 问答检索 488 块校园知识库 → 同时（2026-09 新增）可以在「AI 项目导师」里跟着 AI 从零做出真实代码项目并通过证据化验收，最后拿到一段可写进简历的项目经历。

- **它解决什么问题？**
  1. 校园信息差：7 万字校园指南（22 篇文档、488 块）平铺在飞书里难查，转成可浏览页面 + 即时问答；
  2. 工科学生"缺乏真实项目经历"：没有反馈、没有验收、没有进度的自学困境，用 AI 教练 + 客观验收标准来补。
  （问题 1 见需求文档 v4 §1.2；问题 2 见飞书《Ai导师v2》修改版方案与投资人总结）

- **面向谁？**
  核心用户：暨南大学信科院大一至大四学生（需求文档 v4 §1.3）。
  次级用户：新生家长、考研/保研意向学生、校内外求职者。
  潜在 B 端（仅文档提及，未落地）：高校计算机学院、培训机构、企业新人培训。

- **核心价值是什么？**
  校园侧：消除信息差 + 年级化个性化 + 近零运营成本（纯 BYOK）。
  教学侧：可客观化、可审计的学习成果（Rubric 证据链 + 可量化完成度），而非"AI 说你会了"。

- **当前更接近哪一类？**
  **【已确认事实】它是一个"校园信息平台 + AI 实训工具"的混合体**，同时具备网站、AI 教育产品、游戏化学习系统三类特征。若必须单选：**当前更接近"AI 教育产品"（教学侧为近期投入重心）**，但流量入口与内容主体仍是校园信息平台。

- **定位变化过程**
  | 阶段 | 定位 | 依据 |
  |------|------|------|
  | V1（早期，未见原始文档） | 校园知识库问答/教学平台 | 需求文档 v4 前置版本引用；V2 方案中称 V1 为"教学平台" |
  | V2（2026-09） | 项目交付 + 求职成果（"让学生做出项目 + 写进简历"） | 飞书《Ai导师v2》修改版方案 §1 |
  | 对外口径（时间未知，文档在仓库） | Agent 实战教学平台（C 端学生 + B 端高校/机构） | `docs/AI导师-投资人总结.md` |

  **【存在争议/未决】校园信息平台与 AI 实训平台两条线的重心关系没有最终定论**：现网两者并存（`/chat` 校园问答 vs `/teach` AI 导师），投资人文档把教学线作为主线对外讲，而 PRD v4 的主体仍是校园站。见第 13 章。

**设计理念的形成过程（重要）**

1. **"假登录 + localStorage"**：不引入账号体系与数据库，降低开发与合规成本（无用户数据落库）。理由见需求文档 v4 §2.3。
2. **"纯 BYOK"**：平台不承担模型费用，这是"近零运营成本"的核心手段，也让站点在没有预算的情况下可持续运行。
3. **"证据优先（Evidence First）"**：AI 评审不得凭"看起来合理"判过，必须引用证据；缺证据一律 NEED_REVIEW。理由：教育场景下"放水"比"误判"危害更大，且评审结论需要可审计。
4. **"CI 作为权威系统判定"**：把 GitHub Actions 结论当作 system 判定而非 AI 猜测，因为它是可复现的客观事实。
5. **"产品目标从教学转向交付"**：V2 阶段明确"成功链条 = 需求→项目→AI 辅助开发→项目交付→自动验收→质检陪练→简历描述→求职"，随之砍掉了一批教学向功能（见第 12 章）。
6. **"降低门槛优先于严格性"**：部署要求被降级为三选一，理由是"部署门槛会重创完课率"（V2 方案 修改 1）。
7. **"不确定输出必须规则化"**：所有会影响学生结论的聚合计算（总分、总状态）从 LLM 手里收回代码层。

**当前版本与最初版本的区别（概要）**
最初是"飞书文档 → 检索问答"的单一工具；现在是"登录身份 → 个性化首页 → 内容页面矩阵 → 校园 RAG 问答 → AI 项目导师（指导/验收/陪练/简历产出）→ 成就与双主题"的多模块站点。内容形态从纯阅读扩展到"做项目并交付"。

## 7. AI 导师 / AI 系统设计

### 它解决什么问题
学生缺乏真实项目经历 + 自学无反馈无验收无进度感；通用聊天模型"能答但不知道学生到底会不会"。目标是用"可验收标准 + 证据链"把教学效果客观化【已确认事实，投资人文档 + V2 方案】

### AI 如何"了解"学生
- 前端身份：`xkz_user`（昵称/年级/专业类）+ `Student` 模型（session_id / skills 技能熟练度 / completed_tasks / attempt_count）【已确认事实】
- 会话：后端进程内存 `_sessions`（session_id + task_id 为键），记录最近对话、hint_level、debug_state、last_system_error【已确认事实】
- attempt_count 驱动 Hint Level 与"学习合规"校验（低尝试次数不该拿完整答案）【已确认事实】
- 注意：后端**不持久化**会话；重启丢失（设计如此）【已确认事实】

### AI 如何获得学生代码
GitHub 仓库 URL（可选）→ 见 §6"GitHub/代码提交机制"；另支持直接粘贴代码片段。**不做**部署地址可访问性爬虫验证【已确认事实】

### GitHub 是否作为代码来源
**是主要（但非唯一）来源**，且必须仓库公开可访问；拉不到代码时 Reviewer 只能依据粘贴代码与自述，并在回复中明确告知学生"仓库代码没能被自动读取"【已确认事实】

### 是否考虑学院电脑 / 本地环境
**【未知】**：档案中未见任何关于学院机房统一环境、镜像、代理、内网访问限制的讨论记录。已确认的只有"本地可复现运行"作为验收证据路径、以及"避免 Google Fonts/避免 raw.githubusercontent"这类网络可达性取舍。

### AI 如何检查代码
- 代码证据注入 Prompt 后由 LLM 做语义判定（如"是否存在 POST /chat""Key 是否只在前端之外"）
- 客观部分（CI 结论、证据缺失）由代码直判
- 代码证据只能证明"写了什么"，不能证明"跑没跑通"——运行类必须另有三选一证据（此约束写在 Reviewer Prompt 中）【已确认事实】

### AI 如何评价项目
逐条 Rubric 判定（PASS/FAIL/NEED_REVIEW + evidence + reason）→ 代码层聚合 score/status → 输出 next_step。
**六层输出漂移治理（2026-09-09 实施）**：
| 层 | 措施 | 状态 |
|----|------|------|
| L1 | score 规则化（后端按 weight 加权） | 已实施 |
| L2 | status 规则化（代码判定） | 已实施 |
| L3 | CI 结论直判 | 已实施 |
| L4 | 证据快照冻结 + sha256 | 已实施 |
| L5 | 评审幂等缓存（TTL 600s） | 已实施 |
| L6 | 输出校验兜底（JSON 模式 + Pydantic + 重试 2 次，校验失败丢弃自由文本） | 已存在，保留 |

### AI 是否参与课程验收
**是**，且是唯一验收者（无人工复核环节）。但"是否通过"并非完全交给 AI：证据缺失（precheck）与 CI 结论由代码判定，AI 只负责单条语义判定【已确认事实】

### AI 与课程体系的关系
课程 = 数据（`course_data.py` 硬编码 Course/Project/Stage/Task/Rubric + chunk_key 关联 RAG 素材）；AI 只做运行时行为，不生产课程内容。新增课程需要写代码（**课程工程化/模板化尚未做**，见第 11、12 章）【已确认事实】

### 已经讨论过哪些技术方案
1. 双模式（指导/验收）而非四 AI 角色分工 —— 已落地，前端已收敛为单一入口【已确认事实】
2. CI 结论作为权威证据 —— 已落地【已确认事实】
3. BYOK：Key 只在浏览器 localStorage 与一次性转发请求中，服务端不存储、不落库【已确认事实】
4. 结构化输出（JSON 模式 + Pydantic）替代自由文本 —— 已落地【已确认事实】

6. 检索五路召回 + RRF + 意图加权 + Reranker（Reranker 默认关闭）【已确认事实】
7. 简历描述用"模板 + 数据填充"而非 LLM 自由生成【已确认事实】
8. 转移任务（Transfer Task）作为陪练而非裁决【已确认事实】
9. 课程工程化（course_data 模板化/项目生产工厂）—— **讨论过，暂缓**【讨论方案】
10. RAG 课程的 embedding 成本方案：服务端免费额度 / 课程内置已向量化语料 —— **讨论过，未决定**【讨论方案】

### 哪些方案存在技术风险
- **BYOK 门槛**：未配 Key 用户占比目标 ≤60%（PRD 目标值），但"先配 Key 才能用"是所有 AI 功能的前置卡点，直接影响转化【已确认事实为目标；影响为 AI 推测】
- **知识库语料版权**：课程 RAG 需要"可公开、有版权允许"的语料，目前校园指南来自学生共创，是否可直接作为课程内建知识库**未决**【存在争议/未决】

- **无数据库的规模上限**：评审会话与缓存均在进程内存，重启即丢；多实例部署会不一致【已确认事实 + AI 推测的限制】
- **服务器无法稳定直连 GitHub**：已影响部署流程（改用 bundle），也可能影响 GITHUB_TOKEN 拉取速率与稳定性【已确认事实】
- **LLM 语义判定仍有单条波动**：漂移治理后残留风险在"单条 criteria 判定"层面（同证据可能出现 PASS/FAIL 差异），属已知残留【已确认事实】

## 15. 需要下一位 AI 重点解决的问题

**按"先验证、再扩张"的顺序排列（顺序理由是 V2 方案自己设定的前置条件，不是本文档作者的偏好）**

1. **先确认产品定位的取舍（阻塞级）**
   校园信息平台与 AI 实训平台两条线要不要收敛为一条？对外叙事的"Agent 实战教学平台"与站内主体"校园指南站"不一致，会直接影响下一步该优化什么。**建议问清用户后记录决策，不要自行替他决定方向。**

2. **设计 V2 主链路的真实验证方案（最高优先）**
   当前只有"代码跑通 + 自动化测试通过"，没有任何学生数据。需要：招募多少学生、跑哪门课、看什么指标（完成率 / 验收通过率 / NEED_REVIEW 补交率 / 简历描述是否被真实使用）、收集哪些定性反馈。

3. **审查"AI 验收"的可信边界**
   在 L1~L6 之后，残留的是单条语义判定的波动。需要评估：是否引入抽检（人工复核 x% 的评审结果）、是否需要把更多判定规则化、是否需要给"可讲清数据流向"这类主观项设计更客观的判定标准。

4. **解决 RAG 课程的前置阻塞（若要做课程 03）**
   embedding 成本归属方案（三选一：服务端额度 / 内置向量化语料 / 本地小模型）+ 语料版权来源。二者不解决，知识库类课程无法开课。

5. **补齐文档一致性**
   把 `PROJECT_OVERVIEW.md` 与投资人文档更新到 2026-09 现状（双模式收敛、career/interview 接口、六层漂移治理、三选一证据、48 成就、49 条 Rubric），否则下一位 AI 会被旧文档误导。

6. **评估"课程工程化"是否值得现在做**
   它决定了未来课程扩张的边际成本。判断依据应当是"是否确定要开 3 门以上课程"，而不是技术偏好。

7. **基础设施与工程债的取舍**
   （a）进程内存缓存的失效影响是否可接受；（b）dist 入库与灰度/缓存策略；（c）前端双主题双模板的维护成本；（d）死代码清理；（e）服务器直连 GitHub 的稳定性对运行时拉取代码的影响（需实测，不要假设）。

8. **两条产品线的转化路径**
   如果双线继续并存，需要明确：校园站的学生如何被引导到 AI 导师？AI 导师做完项目的人是否回到校园站？目前首页只有两个并列入口，**没有设计转化路径**。

**给下一位 AI 的工作方式提醒**

- 本项目**没有**数据库、没有真实账号体系、没有监控；所有"用户数据"目前都是空的，不要基于想象中的数据进行优化建议。
- 用户的决策风格：倾向"收敛范围、降低门槛、消除不确定性"，对"过度设计"和"看起来完整但无用的功能"容忍度低（里程碑勾选功能被撤销即为例证）。
- 否决清单（第 12 章）是很硬的约束，**重新提出被否决的方案会浪费用户时间**。
- 项目里存在大量"文档写的是旧状态"的情况，**判断当前实现请以代码为准**。
