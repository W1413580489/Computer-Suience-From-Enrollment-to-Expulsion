# 新课程 · 代码素材征集提示词

> **用途**：把这段提示词发给「能直接访问项目代码的 AI」（例如在项目里打开的 AI 编程助手），
> 让它产出一份结构化的素材文档，交给课程设计方直接编写课程。
>
> **为什么需要它**：课程数据模型（Stage / Task / Rubric / 简历亮点 / 面试题 / 视觉观察点）需要的是
> **特定形态**的信息，而不是一份泛泛的"项目介绍"。按下面的字段要，可以一次拿到位、避免反复追问。

---

## 使用方法

1. 在**那个项目里**新开一个 AI 会话（关键是它要能读代码、跑命令、看 git 记录）
2. 把下面「复制开始 → 复制结束」之间的内容整段粘进去
3. 让它把结果保存为 `COURSE_MATERIALS.md` 放在项目根目录（或直接贴回给你）
4. 把产出交回课程设计方

# 任务：为「把这个项目做成教学课程」准备素材档案

我是这个项目的作者。我打算把它做成一门**动手实战课程**（面向零基础/初学者，学生跟着从零做出一个能跑通的作品）。
课程设计方需要一份**如实、可核对**的素材档案。请你阅读代码后产出。

## 请先做的事

- 读完整源码（优先：入口文件、核心模块、配置文件、测试、文档）
- 看 `git log`（若有）了解演进顺序；看 README / 依赖清单 / 示例配置
- 实际跑一次能跑的命令（构建、测试、启动、示例调用），记录**真实输出**
- 如果某项你无法确认，**写"未知"**，不要猜测、不要编造

## 硬规则（务必遵守）

1. **不许编造**：没看到的文件、没跑过的命令、没验证的行为，一律标"未知"或"未验证"。
2. **引用要精确**：每个结论都带 `文件路径:行号`；贴代码片段时**保持原文**，不要改写或精简掉关键行。
3. **区分三类信息**：`代码里确实有的` / `我跑出来的结果` / `作者的推测与设计意图（需作者确认）`。
4. **不要美化**：不要写宣传文案，不要用"优雅""高效""强大"这类词。就事论事。
5. **不要编造失败经历**：踩坑记录只写代码/提交里能看出来的（报错信息、注释、兼容分支、TODO、试错痕迹）。
6. 用 Markdown 输出，按下面的分节，**节标题原样保留**，便于课程设计方定位。

---

## 0. 项目一句话定位

- 这个项目是什么？（一句话，说清"做什么用的"）
- 解决什么问题？谁会用？
- 当前完成度：能跑通的最小闭环是什么？哪些是半成品/TODO？
- 项目创建时间、最后修改时间（看文件时间或 git 记录）

## 1. 运行与依赖（决定课程的"环境准备"环节）

- 语言 / 运行时版本要求（给出版本约束的确切来源文件与行）
- 依赖清单（直接贴依赖文件的原文）
- 从零开始的完整命令序列：安装 → 配置 → 运行 → 验证"成功了"看到什么
- 需要的外部凭据 / 账号 / 环境变量（变量名 + 用途；**不要写出真实密钥值**）
- 有没有必须联网、必须特定操作系统、或需要额外服务的部分？
- 跑一遍测试：命令 + 实际输出（通过多少条）

## 2. 代码地图

用表格列出每个源文件：

| 文件路径 | 行数 | 职责（一句话） | 关键导出/函数 | 是否必读 |
|---|---|---|---|---|

再说明：
- 哪些文件是**核心关键路径**（去掉就不工作）
- 哪些是**可选/增强**（去掉也能跑）
- 有没有生成物 / 缓存 / 数据库文件被误提交（列出）

## 3. 核心数据流（把一次完整调用讲清楚）

按顺序描述"从触发到结果"的完整链路，每一步写：**入口函数 → 做了什么 → 产物是什么**。
用文字流程即可（可以配 ASCII 箭头图），要具体到函数名。

同时说明：
- 数据存在哪里？（内存 / 文件 / 数据库；数据库的表结构与字段）
- 有没有状态？状态怎么跨调用/跨会话保持？

## 4. 关键实现细节（协议与对外接口）

- 对外暴露的接口 / 命令 / 工具清单，逐个写：**名称 / 参数（名字+类型+是否必填）/ 返回值 / 做什么**
- 用到的协议或第三方 API：调用的端点、请求体关键字段、响应关键字段、错误码含义
- 配置文件的完整字段说明（每个字段：含义 / 默认值 / 是否必填）
- 与外部系统（客户端、平台、数据库）的对接方式和对接点

## 5. 优化点清单 ★重点

把项目里"后来改好了的地方"逐条列出。这是课程的主要亮点，也是简历素材来源。

对每一条：

- **优化点**：一句话（如"改用连接池复用数据库连接"）
- **优化前**：原来怎么做的 + 有什么问题（能贴出旧代码最好）
- **优化后**：现在怎么做的（贴关键代码，带文件:行号）
- **为什么**：这么做解决了什么问题（避免什么后果）
- **效果**：可验证的结果（快了多少 / 少了几次调用 / 修掉了什么错误 / 解决了什么兼容问题）
- **是否必学**：核心必须讲 / 进阶可以讲 / 只有特殊场景才需要

## 6. 踩坑与报错记录

凡代码、注释、提交信息、兼容分支里能看出来的"踩过的坑"，逐条记录：

- **现象**：报错原文（逐字抄）+ 出现在什么操作之后
- **原因**：为什么会这样
- **解法**：怎么改的（贴代码 + 文件:行号）
- **如果不知道原因**：写"原因未知"，不要编

## 7. 从零到一的最短路径 ★重点

假设学生**从空白开始做**，把过程拆成**可独立完成的小步骤**（每步 10~30 分钟能做完、做完有明确可见的结果）。

对每个步骤：

- **步骤名**（说清做什么，不要写"学习 XX"这类学习属性表述，要写"做出什么"）
- **目标**：这一步做完，什么就绪了
- **前置**：需要先完成哪些步骤
- **关键操作**：具体命令 / 需要写的核心代码（给骨架即可）
- **易错点**：这一步最容易错在哪
- **完成标志**：怎么知道这步做对了（**必须是能看到的现象**，如"终端打印出 X"、"客户端里出现 Y"）
- **属于哪一类**：环境准备 / 开发 / 调试 / 测试 / 整理交付

并明确标出：
- **关键路径**：不做就走不下去的步骤
- **可选增强**：不做也能交付，但做了更好（对应第 5 节的优化点）
- 适合分成几个"阶段"？每个阶段一句话目标

## 8. 可验收的"可观察结果"清单 ★重点

课程验收靠"看得到的结果"判定。请列出这个项目里所有**能被第三方观察到、可截图或复制粘贴作为证据**的结果，每条写：

- 观察方式：（终端输出 / 客户端界面 / 文件内容 / 网页 / 日志 / 测试报告）
- 应该看到什么（**具体到文案、字段名、结构**）
- 用来证明哪件事做成了
- 这个结果**不能**证明什么（防止误判）

## 9. 技术名词清单（用于写简历）

只列**具体的技术名词**（语言、框架、库、协议、工具、平台）。

- ✅ 正确示例：`TypeScript`、`SQLite`、`PostgreSQL`、`Vitest`、`JSON-RPC`
- ❌ 不要写：`AI 协作开发`、`工程化能力`、`工作流编排` 这类能力标签

按重要性排序，并注明每个词**在项目里具体用来做什么**（一句话）。

## 10. 值得写进简历的亮点 ★重点

从第 5、6 节里挑 4~8 条最能体现工程能力的，每条写成：

- **亮点短语**（动词开头，如"实现指数退避重试"）
- **目的**：为什么做（避免什么后果）
- **结果**：达成什么效果（有数字/对比最好）
- **归类**：架构设计 / 稳定性与容错 / 结果产出 / 工程素养

注意：**不要写"学习了什么""认识了什么"**——简历只认"交付了什么"。

## 11. 面试自检题（3~5 题）

针对这个项目，写出面试官可能问的问题，每题给：

- **问题**（面试官口吻）
- **参考答案锚点**：1~2 句核心要点（供学生自比，不是标准答案）
- **提示**：答不上来时给的启发
- **类型**：解释原理 / 排查问题 / 换个场景（变式）

## 12. 集成与调试（如果项目要接入其他应用，这一节很重要）

- 接入方式：完整贴出配置示例（配置文件、命令行、注册方式）
- 接好之后**在哪里能看到它生效**（界面、列表、状态指示）
- 官方/可用的调试工具与用法（命令 + 它能看到什么）
- 权限、安全与隐私注意事项（能访问什么、有什么风险、如何收敛）
- 常见接入失败的表现 + 排查步骤

## 13. 不确定 / 未完成 / 需要作者确认的清单

- 你认为**设计意图不明确**的地方
- 代码里**互相矛盾**的地方（如文档与实现不一致）
- **没有测试覆盖**的关键逻辑
- 你**无法验证**的行为
- 已知但没做的 TODO

---

## 输出要求

- 一份 Markdown，节标题与上面的编号一致（缺失的节写"无"并说明原因）
- 篇幅不限，但**每一句都要能被代码验证**
- 代码片段保留原文；引用格式统一为 `路径:行号`
- 不确定的地方明确写"未知"，不要为了完整而编造

```
另外，因为这是 MCP 项目，请在第 4 节和第 12 节里额外补充：

1. 服务端三元能力清单，分别列出（没有的写"无"）：
   - Tools：每个工具的 name / description 原文 / inputSchema（完整贴） / 返回结构 / 是只读还是写入
   - Resources：每个资源的 URI 模板 / 返回内容 / MIME

3. 客户端接入：分别给出在常见 MCP 客户端里的**完整配置 JSON 原文**（含字段含义）
4. 调试过程：用官方调试工具的完整命令、看到的界面/输出长什么样
5. 数据持久化：数据库文件位置、表结构、如何初始化、如何清空重来
6. 边界与安全：这个 server 能读写哪些数据？有没有越权风险？做过哪些收敛（如路径校验、只读模式、大小限制）？
7. 兼容性处理：有没有针对不同客户端/不同版本做的兼容分支？（这类地方往往是课程里最有价值的"坑"）
```

## 给课程设计方（我）的最小可用清单

如果对方产出的文档不完整，至少要拿到这 6 项才能开始设计课程：

1. **从零到一的最短路径**（第 7 节）→ 直接变成 Stage / Task
2. **可观察结果清单**（第 8 节）→ 直接变成 Rubric 的达标条件与视觉观察点
3. **优化点清单**（第 5 节）→ 变成简历亮点（resume_points）
4. **踩坑记录**（第 6 节）→ 变成 Task 的 hints
5. **技术名词 + 亮点**（第 9、10 节）→ 变成 Project 简历素材
6. **面试自检题**（第 11 节）→ 变成质检陪练题目
